**Status: accepted by the owner (2026-11-26).** The answers are below. The tickets in Linear carry the decision and the acceptance criteria. The arena ran on 2026-11-26 together with FAC-306 and FAC-310, because the listing texts depend on both. The process is in [FAC-305-process.md](FAC-305-process.md). The adopted prototype is [FAC-305-306-prototype.diff.txt](FAC-305-306-prototype.diff.txt) (base `e3cebf2`; apply with `git apply`). The probes are in [FAC-305-306-tools/](FAC-305-306-tools/).

Criteria: (1) the domain model stays simple, (2) respect the module system, (3) don't grow the scope (first Unlisted submission as soon as possible), (4) works and fits, proven by running it.

## What the extension reads today (measured)

- **Every** tab's URL is stored in `chrome.storage.session` from the moment the worker starts. That covers every window, and tabs opened later too. The fragment is stripped; the query is kept. This was measured on the released 0.2.1 ZIP in a fresh profile that never opened Linklog: the install opens `connect.html`, and `instances` already holds the URLs. The read is `init()` → `registry.reconcile(await chrome.tabs.query({}))`, plus the tab listeners.
- Titles are read only when a Linklog page asks for a snapshot.
- The extension itself makes **zero** network requests; `apps/extension/src` has no `fetch`. Data leaves the browser only from the Linklog page:
  - the tab list (URLs, titles, icons, groups) of Linklog's window goes over the bridge when Browser view opens;
  - page text and URL go to `/api/browser/evaluations` when an active lens evaluates a tab, and the Worker sends them to a remote AI provider;
  - Save sends only URLs, and the library fetches them through its extraction pipeline.

So "Allow page content" covers page text, but nothing covers the URL reads that start at install.

## Decision

**Option 1: an explicit accept step in the extension. Until the user accepts, the extension runs nothing that touches tabs.**

- **The flag.** One persisted flag, `consent: true` in `chrome.storage.local`. The **Accept and connect** button on the Connect page writes it. The background listens to `chrome.storage.onChanged`, so no new message type is needed.
- **Before consent:**
  - `init()` does not run: no `tabs.query`, no registry, no group reads, no `installationId`.
  - Tab and group events are dropped.
  - The bridge answers every Linklog request with the protocol constant `CONSENT_REQUIRED`. The one exception is `openPermissions`, which opens `connect.html` next to the Linklog tab and reads no tab data.
  - Measured on the packaged build: `storage.session = {}`, `storage.local = {}`.
- **After consent:**
  - `init()` runs as it does today. The flag survives worker and browser restarts; uninstalling removes it.
  - Measured: `hello` works, the snapshot lists the tabs, and the extension still makes no network requests.
- **The Connect page.** A consent card (disclosure, **Not now**, **Accept and connect**) replaces the permissions card until consent. After Accept, the permissions card ("Allow page content") appears as it does today. Page access stays a second, separate step with Chrome's own dialog.
- **Declining.** "Not now", or closing the tab, leaves a clear "not connected" state everywhere:
  - The popup shows "Linklog pages: Not connected" and **Review and connect**.
  - The Connect page says "Not connected. Linklog reads nothing; accept here whenever you want."
  - Linklog's Browser view gets one new connection state, `consent`: "Not connected yet. The Linklog extension reads nothing until you accept on its Connect page…" with an **Open Connect page** button. It retries, so it connects by itself after Accept.
- **Updating from 0.2.x.** Users who update go idle until they accept. Measured on the real 0.2.1 ZIP updated in place:
  - Connect does not open, because `onInstalled` opens it only on `install`.
  - `storage.session` is empty. `storage.local` keeps the old `installationId` and linked-group hints, unread and unsent.
  - The popup says "Not connected". After a page reload, Browser view shows the consent card. After Accept, the linked group binds again.
- **Size.** 16 files, +161/−45:
  - extension +135/−44;
  - web +17;
  - protocol +5;
  - test seeding +4.

  This is more than the "about +100" the moderator first promised; round 3 counted it. Not counted: the ADR, docs, the workflow comment and the new browser-test check.

### Why, against the criteria

- **Policy.** Option 1 is the only reading that satisfies every rule in the [User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq?hl=en). Local storage counts as handling ("disclose how they handle user data, even when data is processed or stored locally"). Consent must come "before collecting or handling user data". And "the prominent disclosure and consent must occur within the Product's user interface." The read starts when the worker starts, before any UI exists. So option 2 cannot meet "before collecting" without moving the read behind a gate, and that gate is already option 1.
- **Criterion 1.** One boolean, no consent version, no timestamp. The debaters swapped on this point, `consentAt` vs `consent`; the moderator chose the boolean as the smaller model. A version to ask again when the disclosure changes is future scope.
- **Criterion 2.** The gate lives in `background/index.ts` only. `commands.ts` only gets `openConnectPage()`; the pages write the flag and render it; the bridge is unchanged; the protocol gains one constant; the web gains one state.
- **Criterion 3.** No withdraw flow, no per-site picker, no new message type.
- **Criterion 4.** Proven with the consent probe, the startup-read probe, the upgrade probe from 0.2.1, typechecks and 118 unit tests. `test:browser` was not conclusive on a loaded machine (see [process](FAC-305-process.md#test-browser)), so a clean run is an acceptance criterion.

## The disclosure (Connect page, English)

> **Before Linklog reads your tabs**
> This extension shows your open tabs in Linklog's Browser view. It reads nothing until you accept.
>
> If you accept, the extension:
> - **Reads the address (URL) and title of every open tab, in every Chrome window, and your tab groups.** The tab list stays in Chrome's memory until Chrome closes. The name and color of groups you link to Linklog stay on this device, so they can be linked again after a restart.
> - **Sends the tabs of Linklog's window** (URLs, titles, icons, groups) to the Linklog page when you open Browser view.
> - Only if you also allow page content: **reads the text and preview of open pages**. When a lens you turned on evaluates a tab, its URL and text go to your Linklog library, whose server sends them to a remote AI provider for the answer.
> - When you save a tab, sends only its URL. Linklog's server then fetches the page and extracts its content with a remote extraction service, like any link you add.
>
> Never cookies, passwords or form fields. Your data isn't sold or used for ads. The providers we use are named in the [privacy policy](https://linklog.facundopri.com/privacy).
>
> [Not now] [Accept and connect]

The listing carries the short form (see [FAC-310](FAC-310.md)). The manifest `description`, which is the store's short description, says "It reads tab URLs and titles only after you accept." So the user sees it before installing, and Chrome's own install dialog adds "Read your browsing history." This is how the arena reads "prior to installation" in the Policies together with "within the Product's user interface" in the FAQ: the listing discloses before install, and the in-product Accept obtains consent before any collection. No source confirms that a reviewer accepts that pairing. It remains in the research doc's "No verificado".

## Alternatives dropped

- **Option 2 (Connect page as the consent, with a written justification).** The read starts at install, before any action. Opening Browser view happens in the web app, not in the extension UI, and does not agree to any disclosure.
- **`hello` succeeds with `HelloAck.tabAccess: false`** (debater B, round 1). It is the more typed model, but it needs `init()` to run before consent, because `hello` returns the ids. It also spreads consent over `hub`, `commands` and `index`, and adds an exemption that lets `openPermissions` run before `hello` on any page. B adopted A's gate in round 2.
- **Reusing the "Allow access" banner** (moderator claim C2). That banner renders only once a snapshot exists, which means tab data was already sent. A bare error maps to `missing`, and the web then tells an installed user to download the extension. Both debaters refuted the claim by running it.
- **An empty snapshot so the existing banner shows.** The page would show "0 tabs" for a window that has tabs.
- **Wiping 0.2.x `storage.local` on update.** That data was collected under 0.2.x, is never read before consent, and the disclosure already names it. Wiping it adds code and loses group re-binding.

## Proposed ticket changes (FAC-305)

Replace "Owner decision needed first" with "Decided: option 1 (see `docs/grills/FAC-305.md`)". Replace the acceptance criteria with:

- A fresh install of the packaged build stores nothing in `chrome.storage.session` or `chrome.storage.local`, and makes no network request, until **Accept and connect** is clicked. The bridge answers `CONSENT_REQUIRED` to every request except `openPermissions`.
- After Accept: Browser view lists the tabs without a page reload, and the flag survives a browser restart.
- An update from 0.2.x reads nothing until Accept, and linked groups bind again after it.
- The Connect disclosure is the text above, with the privacy policy link `https://linklog.facundopri.com/privacy` (FAC-307, PR #56). It names URLs, titles and groups in every window, page content, the remote AI provider and remote extraction, and what stays on the device.
- **Not now** leaves the popup, the Connect page and Browser view in the "not connected" state described above. Browser view connects by itself after a later Accept.
- `test:browser` gets one check that does not seed the flag: Browser view shows "Not connected yet", clicking Accept on Connect makes it list the tabs, and storage is empty before Accept. The rest of the suite keeps seeding `consent: true`.
- The release notes in `extension-release.yml` say to accept on the Connect page first.
- ADR 0005 is accepted. The handoff doc's §Permisos describes the gate.
- The version rises to 0.3.0 in `apps/extension/package.json`.
- How to verify: the consent probe from `docs/grills/FAC-305-306-tools/` on the packaged ZIP; `bun run test:browser` passing in one clean run on a quiet machine (check the load average first; a failing privacy check is a finding, never a flake); and screenshots of Connect before and after Accept and of Browser view's `consent` state.
- Ship it in the same PR as FAC-306: both change `apps/extension/` and need one version bump. The web state and the extension ship on the same push to `main`. The deploy and the GitHub release are separate workflows, so they land minutes apart. An old web page with the new extension shows the install card until it is reloaded, which is cosmetic and short.
