## Findings and scope

- **Offline remains the default.** `scripts/demo.ts:10` still supplies `LINKLOG_WRANGLER_LOCAL=1` when unset. The new package command explicitly selects `0`; the string `0` survives the existing `||=` default. `scripts/dev.ts:30–31,50` uses the same exact comparison for the Worker capability flag and Wrangler `--local`, preventing a normal launcher/guard disagreement. The generated env file comes after `.dev.vars`; migrations still always use `--local`.
- **Connected mode is explicit and its cost is disclosed.** The command does not add Wrangler `--remote` for the entire Worker; it enables the existing binding-level `remote:true` configuration for Browser/AI. The checked-in D1/R2 bindings have no remote override, and email remains locally simulated. Existing port-conflict refusal and state/secret reuse remain unchanged. Ordinary `dev` behavior and explicit environment overrides are also unchanged; these guarantees assume the checked-in Wrangler configuration, not an arbitrary custom config supplied by the caller.
- **The guard handles the actual failure boundary.** `web.ts:7` rejects before destination validation, `measured`, and `quickAction`; `social.ts:59` guards the rendered fallback while preserving the existing public-HTML attempt. `browser-run.ts:3` applies the mode flag only to `local`/`test`; production and preview bindings are not disabled by a stray `LOCAL_SERVICES_ONLY=1`. An absent binding is still unavailable in any environment.
- **No fabricated extraction success.** Offline web extraction throws an actionable error. The existing workflow failure path persists a failed job/content error rather than synthetic Markdown. Existing usable social public-HTML content can still succeed without Browser rendering. Manual text storage does not depend on this capability; its ownership and active-job checks remain intact.
- **Capability claim should remain narrow (non-blocking, inherited).** `worker/store.ts:21` now correctly advertises Markdown/Browser availability. The untouched `:22–27` still reports `jev:true` from an AI binding alone, including an offline local env: `capabilities({APP_ENV:"local",LOCAL_SERVICES_ONLY:"1",BROWSER:{},AI:{}})` returns `{provider:"cloudflare",markdown:false,jev:true}`. Do not describe this patch as fixing every service capability or proving offline AI works. This is not a regression introduced by the Browser fix and is not a blocker for its stated scope.

The documented root cause is consistent with current official [Cloudflare Quick Actions requirements](https://developers.cloudflare.com/browser-run/quick-actions/): compatibility date at least 2026-03-24 and remote Browser service access for local development. The repository uses 2026-09-21. The coordinator's [minimal actual-service comparison](browser-rpc-evidence-2026-10-09.md)—local RPC error versus remote HTTP 200 / 9,089 Markdown characters for the same URL—is inherited evidence, not a cloud call independently repeated by this reviewer.
