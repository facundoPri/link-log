## Lo que existe en este worktree

- React 19 se sirve con Bun y HMR en `127.0.0.1:3000` durante desarrollo. El proxy de [`src/index.ts`](../../src/index.ts) reenvía `/api/*` a Wrangler en `127.0.0.1:8787`, quitando `Host` y `Origin` antes de la petición interna. [`src/api.ts`](../../src/api.ts) usa `fetch('/api…')` del mismo origen visible al navegador y no envía un token explícito. En producción, [`wrangler.jsonc`](../../wrangler.jsonc) prevé un solo Worker con Static Assets SPA y `run_worker_first: ['/api/*']`.
- La API de [`worker/index.ts`](../../worker/index.ts) rechaza hosts distintos de loopback y compara `Origin` en escrituras, pero **no autentica ni autoriza**. Ese guardia no es una sesión ni una política de usuarios. `/api/library` devuelve tablas completas; las consultas por ID, mutaciones, cancelación de lotes, contenido y uso no filtran dueño. No se encontró código de extensión en este checkout; sus límites de conexión se tratan abajo como requisito futuro, sin dar por verificada una implementación de otra rama.
- [`migrations/0001_library.sql`](../../migrations/0001_library.sql), [`0003_context_and_evaluations.sql`](../../migrations/0003_context_and_evaluations.sql) y [`0006_lenses.sql`](../../migrations/0006_lenses.sql) crean `links`, `tags`, `lenses`, `batches`, `jobs`, resultados y `usage_events` sin `user_id`. URL original, nombre de tag y nombre de lens son únicos globalmente. [`worker/store.ts`](../../worker/store.ts) arma la biblioteca con lecturas globales; [`worker/jobs.ts`](../../worker/jobs.ts) guarda IDs en D1 y los envía a Queue/Workflow, con recuperación por cron. Los Markdown viven en R2 bajo `links/<linkId>/…`; la lectura y eliminación usan el ID del link.
- [`scripts/dev.ts`](../../scripts/dev.ts) aplica migraciones D1 **locales** antes de iniciar Wrangler, y simula cron cada 30 s. El README declara que no hay despliegue ni base remota; el `database_id` de Wrangler es un placeholder local. Por lo tanto, migrar los links existentes a una cuenta remota exige un paso explícito de exportación/importación y asignación de dueño, no sólo ejecutar migraciones de esquema. [D1 distingue `--local` y `--remote`](https://developers.cloudflare.com/d1/wrangler-commands/) (acceso: 28-09-2026).

### Qué es identidad de usuario y qué no lo es

**Access** es un proxy con políticas de Zero Trust para permitir entrar a una aplicación. Puede autenticar personas mediante un IdP o [PIN por email](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/), proteger un Worker completo o un [Custom Domain](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/), y entregar identidad verificable. Si se protege sólo un hostname/ruta, hay que inventariar `workers.dev`, previews y cualquier otro dominio; la protección a nivel Worker cubre todos sus dominios. La [documentación de Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) distingue esas coberturas. Access da control de acceso al sitio, pero no define el modelo de propiedad, suscripciones ni permisos dentro de Linklog. Su `sub` está documentado como único por email y organización, **pero puede cambiar si se borra y vuelve a añadir el usuario**; no conviene usarlo como clave primaria durable de `links` o facturación. [Token de aplicación](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/) (acceso: 28-09-2026).

Los [service tokens de Access](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/) identifican sistemas automatizados mediante Client ID + secreto; el ejemplo de JWT de servicio tiene `sub` vacío. No deben convertirse en la identidad humana de los links. [API Shield JWT validation](https://developers.cloudflare.com/api-shield/security/jwt-validation/) verifica un JWT existente, no emite cuentas ni sesiones. [Turnstile](https://developers.cloudflare.com/turnstile/get-started/) verifica una prueba antibot del formulario, no al dueño de una biblioteca. La [Workers OAuth Provider Library](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/) ayuda a emitir autorización OAuth para clientes como MCP, pero requiere configurar un método de login/IdP; no sustituye el login de usuarios de Linklog. “Cloudflare como proveedor OAuth” de Better Auth inicia sesión con **cuentas Cloudflare**, no convierte Access en un proveedor de cuentas públicas de Linklog. [Integración Cloudflare de Better Auth](https://better-auth.com/docs/authentication/cloudflare) (todos, acceso: 28-09-2026).

## Compatibilidad y operación que afectan la decisión

**Better Auth.** La guía oficial muestra `database: env.DB` para D1 nativo y el [adaptador Drizzle](https://better-auth.com/docs/adapters/drizzle) como alternativa. El [ejemplo para Workers](https://better-auth.com/docs/integrations/hono) requiere `nodejs_compat` por `AsyncLocalStorage`, bandera que este `wrangler.jsonc` ya declara. El handler puede montarse en la ruta existente sin adoptar Hono; eso es una inferencia de su API `Request → Response` y requiere spike con la versión fijada. Las sesiones se guardan por defecto en la base: cookie `session_token`, tabla `session`, expiración predeterminada de siete días y renovación; el cache adicional en cookie es opcional. Las [cookies](https://better-auth.com/docs/concepts/cookies) son `HttpOnly` y `Secure` en producción, y la documentación advierte sobre dominios cruzados. El primer intento debería mantener app y API bajo **un único origen público** y verificar que `localhost:3000` → proxy → `127.0.0.1:8787` conserva callback, `Set-Cookie`, logout y `trustedOrigins`; la configuración `baseURL` será distinta entre local y dominio real. [Sesiones](https://better-auth.com/docs/concepts/session-management), [cookies](https://better-auth.com/docs/concepts/cookies), [Hono/Workers](https://better-auth.com/docs/integrations/hono) (acceso: 28-09-2026).

Better Auth documenta [email + contraseña](https://better-auth.com/docs/authentication/email-password), [social OAuth](https://better-auth.com/docs/authentication/google), [magic link](https://better-auth.com/docs/plugins/magic-link), [email OTP](https://better-auth.com/docs/plugins/email-otp) y [passkeys](https://better-auth.com/docs/plugins/passkey); estos últimos requieren tablas adicionales y origen/RP ID correcto. Envío de correo y credenciales OAuth quedan a cargo de la integración elegida. Cloudflare [Email Sending](https://developers.cloudflare.com/email-service/) ofrece una opción nativa de envío, **todavía beta y en Workers Paid**; no se debe asumir entregabilidad, cuota o costo adecuados sin elegirla y probarla. Su [plugin Captcha](https://better-auth.com/docs/plugins/captcha) admite Cloudflare Turnstile como defensa de endpoints. Para FAC-44, el [plugin API Key](https://better-auth.com/docs/plugins/api-key) documenta claves de usuario con expiración y permisos, mientras [OAuth 2.1 Provider](https://better-auth.com/docs/plugins/oauth-provider) documenta autorización delegada y PKCE; **no se probó ninguno con D1 ni con una extensión de Linklog**. El catálogo también incluye `better-auth-cloudflare`, expresamente [comunitario, no oficial ni verificado](https://better-auth.com/docs/plugins/community-plugins); no es requisito para usar el binding D1 nativo. No añadir plugins sólo por disponibilidad. Las [migraciones](https://better-auth.com/docs/concepts/database) del adaptador D1 nativo se pueden generar y revisar como SQL; con Drizzle hay que generar esquema y aplicar sus migraciones. Versionar esas migraciones junto a las de Linklog y aplicarlas en local y remoto por separado. Better Auth indica que D1 usa `batch()` y no transacciones interactivas; algunas funciones como [SCIM](https://better-auth.com/docs/plugins/scim) exigen esas transacciones y no son compatibles. Su [rate limit](https://better-auth.com/docs/concepts/rate-limit) guarda contadores en memoria por defecto, inadecuado para asumir protección distribuida en Workers: evaluar D1 o almacenamiento secundario y sus migraciones. El sitio registra **1.7.6 (24-09-2026)** con correcciones para D1; el [changelog](https://better-auth.com/changelog), la [política de seguridad](https://github.com/better-auth/better-auth/security) —soporte sólo de la última versión— y la [guía 1.7](https://better-auth.com/docs/guides/1-7-upgrade-guide) exigen revisar esquema y upgrades, no instalar una versión flotante. [D1 1.5](https://better-auth.com/blog/1-5) (fuentes consultadas: 28-09-2026).

**Cloudflare Access.** Las [cookies de Access](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/) son propias de Access; la duración se configura por política/app y su valor por defecto documentado es 24 h. Para la cookie de la aplicación, `HttpOnly` y `SameSite` son configurables. La tabla de esa página marca `HttpOnly` como “Admin choice (Default: None)”, pero el texto posterior dice que está habilitado por defecto: **la documentación es contradictoria en ese valor**. Verificar atributos reales y compatibilidad con Browser/extensión en el spike. El [logout](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/) puede enlazar `/cdn-cgi/access/logout`, revoca la sesión de Access entre aplicaciones y tarda 20–30 s en invalidar tokens emitidos; no es un borrado de sesiones de Linklog porque no existirían sesiones propias. El [JWT](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) debe validarse criptográficamente con JWKS rotatorio y audiencia/issuer; confiar en la presencia del header no basta. La documentación reciente permite simular identidad en `wrangler dev` con `access.dev`, pero ese mecanismo usa `ctx.access` y **no salva el límite de Static Assets** de esta configuración: el spike debe ensayar el JWT real o una disposición alternativa, sin llamar “probado” al mock. Protección de Access a nivel Worker [no admite WebSockets](https://developers.cloudflare.com/workers/configuration/cloudflare-access/); si el Browser futuro los usa, evaluar protección por hostname u otra topología. Una ruta por Custom Domain requiere zona Cloudflare y despliegue; ninguno existe en este checkout. (Fuentes consultadas: 28-09-2026.)

## Consecuencias de arquitectura de Linklog

1. **ID interno estable.** Crear un `app_user_id` inmutable en D1. Con Better Auth, mapearlo al `user.id` estable de su tabla; con Access, mantener tabla propia de cuentas e identidades externas (`issuer`, `subject`, `app_user_id`) y un procedimiento explícito para relink al cambiar el `sub`. No usar email como clave de propiedad ni inferir que dos IdP con el mismo email son automáticamente una cuenta. Para [FAC-49](https://linear.app/facundopri/issue/FAC-49/research-payment-providers-and-cost-based-plans-paddle-creem), guardar suscripciones, webhooks y entitlements contra `app_user_id`, con referencias externas de billing separadas; un service token no recibe plan humano por sí mismo.
2. **Migración sin perder lo local.** Inventariar links, tags, lenses, `link_tags`, evaluaciones, `lens_results`, media, `batches`, `jobs`, `usage_events`, `settings` y claves R2 antes de exportar. Definir quién reclama esos registros locales; migrarlos sólo a esa cuenta tras confirmación y con copia/rollback. D1 local y remoto son distintos. Cambiar `UNIQUE(original_url)` y `UNIQUE(tags.name/lenses.name)` globales por reglas por dueño o decidir cuáles definiciones son compartidas. La deduplicación y los alias normalizados deben comprobarse **dentro de un dueño**, sin que una URL de B revele ni reetiquete el link de A. Los registros derivados deben apuntar a recursos del mismo dueño; conservar el historial de evaluaciones y uso.
3. **FAC-41 y procesos asíncronos.** El `user_id` validado debe entrar en cada lectura/escritura por ID, `/api/library`, `/api/usage`, contenido R2, lotes y tags/lenses. Queue y Workflow parten de IDs internos de D1; antes de crear un job hay que comprobar la propiedad y después resolver el dueño del job desde D1, no de un cuerpo de petición ni header no validado. El prefijo R2 actual evita colisiones por link ID, **pero no autoriza**: la comprobación debe preceder a `get`, `put`, borrado y URLs derivadas. Probar dos cuentas, incluyendo peticiones directas al ID ajeno y espera de jobs; FAC-41 mantiene esa responsabilidad y FAC-40 no la da por completada.
4. **FAC-44 y Browser/extensión.** El cliente web actual enviaría cookies del origen visible si se agregara una sesión; hoy no hay sesión. El futuro endpoint de URL de [FAC-44](https://linear.app/facundopri/issue/FAC-44/implement-a-secure-url-only-upload-api-with-plan-aware-limits) requiere decidir clientes: sesión de navegador, token personal revocable y con alcance, o OAuth público con PKCE si otros clientes necesitan autorización delegada. Una clave de servicio de Access serviría para un proceso controlado, no probaría a qué usuario pertenece una URL. Una extensión no debe asumir que `windowId`, `Origin`, permiso de host o estar conectada al Browser autentican al dueño: se necesita un vínculo explícito con la cuenta, renovación/revocación y comprobación del dueño en la API. Better Auth tiene una [guía oficial de extensión](https://better-auth.com/docs/guides/browser-extension-guide) que pide `host_permissions` y `trustedOrigins` con el ID concreto `chrome-extension://…`; advierte contra `chrome-extension://*`. Es un ejemplo Plasmo, no una prueba de la arquitectura MV3 de Linklog. El checkout actual no contiene la extensión; no está verificada su interacción con cookies, CORS, redirecciones de Access o sesión de Better Auth. Webhooks de procesamiento son una decisión aparte y requerirían firma, reintento e idempotencia. (Guía consultada: 28-09-2026.)
5. **Límite de seguridad.** El guardia loopback debe seguir cerrado hasta que haya autenticación y autorización probadas; proteger sólo la UI o `POST` deja expuestos `GET` y rutas directas. Mantener defensa CSRF/origen para cookies, `SameSite`/`Secure`/`HttpOnly` según el dominio, y no tratar el proxy local como frontera confiable en producción. Antes de exponer datos, provisionar D1/R2 remotos, secretos y dominio, probar rutas `workers.dev`/preview y controles de abuso/limites de FAC-49.

## Recomendación provisional y validación mínima

**Si se decide lanzamiento público multiusuario:** llevar a un spike **Better Auth con D1 nativo** (confianza **media**). Tiene soporte explícito de D1, un modelo de usuario/sesión propio de la app y caminos documentados para OAuth, email y passkey; evita una capa de ORM obligatoria sobre el SQL existente. Esta es una recomendación de investigación, **no aprobación de proveedor**. No se ha ejecutado Better Auth ni un flujo OAuth/email en este worktree, y la compatibilidad de cada plugin con esta configuración aún no está demostrada.

**Si se decide beta privada controlada:** considerar **Access** para cerrar el perímetro con OTP/IdP y menos UI de login (confianza **media para protección de entrada; baja para identidad en el Worker actual**). Requiere probar recepción y validación de JWT detrás de Static Assets o cambiar topología; además exige el mismo trabajo de dueño por recurso. Para uso estrictamente local, mantener loopback cerrado puede ser suficiente mientras se define producto, sin presentar eso como release multiusuario.

Spike acotado, **después** de la decisión sobre tipo de lanzamiento y antes de implementar FAC-40/FAC-41:

1. Fijar una versión de Better Auth y, en un cambio experimental descartable, montar `/api/auth/*` con D1 local; generar/revisar migraciones sin tocar los datos existentes. Verificar arranque en Wrangler con `nodejs_compat` y el tamaño/errores de build.
2. Con el proxy `localhost:3000` → `127.0.0.1:8787`, registrar/iniciar sesión con un método elegido, leer sesión, salir, reiniciar Worker y repetir; capturar cookies, callback, `Origin`, `trustedOrigins` y rechazos anónimos en `GET` y escrituras. Repetir bajo un Custom Domain de prueba sólo si se autoriza un despliegue.
3. Si Access sigue en consideración, montar el mismo layout de Static Assets en un entorno de prueba y comprobar si llega `Cf-Access-Jwt-Assertion`; validar JWKS, `iss`, `aud`, expiración y ausencia de `sub` de servicio. Verificar login/logout, OTP/IdP elegido, rutas alternativas y dos identidades. `access.dev` sólo sirve como prueba parcial.
4. En un fixture separado de dos usuarios, ensayar identidad estable, ownership por URL, tags/lenses, contenido R2, jobs/uso y rechazo directo del ID ajeno. Hacer un ensayo reversible de importación local → remoto con conteos e historial intactos. Evaluar el cliente de FAC-44 y la extensión con credenciales apropiadas antes de diseñar tokens definitivos.

## Decisiones para el dueño

1. ¿El primer release queda **privado/local o por invitación**, o será **público multiusuario**? ¿Habrá una etapa privada desplegada con Access?
2. ¿Qué login inicial se desea realmente: email OTP/magic link, contraseña, Google/GitHub/Cloudflare OAuth o passkey? ¿Quién enviará correo y gestionará recuperación? ¿Es aceptable depender de una cuenta Cloudflare o de Zero Trust para cada usuario?
3. ¿A qué cuenta se adjudican los links locales actuales? ¿Tags y lenses serán por usuario o definiciones compartidas? ¿Se permite vincular identidades externas y bajo qué verificación?
4. ¿Qué clientes tendrá FAC-44 (script propio, terceros, extensión), y necesitan acceso delegado o sólo tokens personales? ¿El Browser futuro usará WebSockets?
5. ¿Se planifican planes pagos desde el lanzamiento o más tarde? La selección de Paddle/Creem, precios, límites y elegibilidad sigue en FAC-49; sólo se propone reservar `app_user_id` como clave de entitlements.

**Límite de evidencia:** se inspeccionó este worktree y documentación oficial en las URLs enlazadas el 28-09-2026. No se configuraron proveedores, secretos, Access, D1 remoto ni dominio; no se probó ningún flujo real de login o aislamiento de usuarios. La aprobación del dueño es requisito explícito antes de implementar autenticación.
